# Проектирование базы данных кинотеатра

## Модель данных

Физическая схема находится в [schema.sql](../database/schema.sql), а ER-диаграмма — в [erd.mmd](erd.mmd). SQLite включён в режиме WAL и проверяет внешние ключи для каждого соединения.

| Сущность | Назначение | Основные атрибуты |
| --- | --- | --- |
| `users` | Учётные записи и роли | `email`, `password_hash`, `role` |
| `auth_sessions` | Серверные сеансы входа | хеш токена, CSRF-токен, срок действия |
| `movies` | Фильмы каталога | название, описание, длительность, рейтинг, активность |
| `halls` | Залы и размер схемы | название, число рядов и мест, активность |
| `seats` | Физические места зала | зал, ряд, номер |
| `screenings` | Показы фильмов | фильм, зал, начало, описание, базовая цена, статус |
| `bookings` | Заказ пользователя | сеанс, код, режим, статус, сумма, срок брони |
| `tickets` | Место и цена в заказе | заказ, сеанс, место, цена, статус |
| `audit_log` | Действия администратора | исполнитель, действие, сущность, данные изменения |

## Связи и ключи

- фильм и зал имеют связь один-ко-многим с сеансами;
- зал имеет связь один-ко-многим с местами;
- пользователь имеет связь один-ко-многим с заказами и сеансами входа;
- заказ принадлежит одному сеансу и содержит один или несколько билетов;
- билет ссылается на физическое место и дублирует идентификатор сеанса для быстрой и строгой проверки уникальности.

Первичные ключи — целочисленные surrogate keys. Естественные ограничения заданы отдельно: уникальны адрес пользователя, название зала, место внутри зала, код заказа и начало сеанса внутри зала.

## Нормализация

Схема приведена к третьей нормальной форме. Данные фильма не копируются в сеанс, параметры зала не копируются в место, а реквизиты пользователя не копируются в заказ. Поля `tickets.screening_id`, `tickets.price_cents` и `bookings.total_cents` являются контролируемой денормализацией:

- `screening_id` позволяет частичному уникальному индексу запретить две активные записи одного места на одном сеансе;
- цена билета сохраняет историческую стоимость после изменения цены сеанса;
- сумма заказа исключает повторный пересчёт исторического документа.

## Ограничения целостности

Типы статусов и ролей ограничены `CHECK`. Размеры залов, длительность и цена имеют допустимые диапазоны. Внешние ключи не позволяют удалить используемый фильм, зал, сеанс или место. Частичный индекс `uq_active_ticket` охватывает только статусы `reserved` и `paid`; отменённая или истёкшая запись больше не блокирует место.

## Индексы и запросы

- `idx_screenings_movie_start` ускоряет расписание фильма;
- `idx_screenings_hall_start` ускоряет проверку занятости зала;
- `idx_bookings_user_created` ускоряет личный кабинет;
- `idx_bookings_expiry` ускоряет освобождение просроченных броней;
- `idx_tickets_screening_status` ускоряет построение схемы занятости;
- `idx_auth_sessions_expiry` ускоряет очистку сессий.

Публичный каталог кэшируется на 30 секунд в памяти приложения. Схема мест не кэшируется, потому что её доступность меняется при каждом заказе.

## Транзакции и конкуренция

Оформление заказа начинается с `BEGIN IMMEDIATE`. Внутри одной транзакции приложение освобождает просроченные брони, проверяет сеанс и принадлежность мест залу, проверяет занятость и вставляет заказ с билетами. Даже при одновременных запросах частичный уникальный индекс остаётся последней линией защиты: конфликт завершает всю транзакцию без частичного заказа.

## Безопасность данных

SQL-запросы используют параметры. Пароли хранятся как хеш с индивидуальной случайной солью: применяется `scrypt`, а в сборках Python без него — PBKDF2-HMAC-SHA256. В таблице сессий хранится SHA-256 хеш случайного токена, а не значение cookie. Административные изменения записываются в `audit_log`; поля с паролями из журнала исключаются. Скрипт `scripts/backup.py` использует SQLite Backup API: согласованная копия учитывает WAL и проверяется через `PRAGMA integrity_check` без остановки сервера. Сам файл БД не зашифрован; доступ ограничивается правами ОС, публичная передача данных защищается HTTPS.
