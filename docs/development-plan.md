# План разработки веб-приложения кинотеатра

## Подход

Проект выполняется как монолит: интерфейс, API, бизнес-логика и доступ к SQLite находятся в одном развёртываемом приложении. Это соответствует заданию и снижает стоимость локального запуска. Границы модулей сохранены, поэтому базу данных или HTTP-сервер можно заменить без переписывания правил бронирования.

## Этапы и зависимости

| Этап | Результат | Зависит от | Оценка |
| --- | --- | --- | --- |
| 1. Уточнение требований | Роли, FR/NFR, сценарии, границы версии | — | 0,5 дня |
| 2. Проектирование данных | ER-модель, ограничения, индексы, миграционная схема | 1 | 1 день |
| 3. Каркас сервера | Конфигурация, инициализация БД, маршрутизация, ошибки | 2 | 1 день |
| 4. Учётные записи | Регистрация, вход, роли, сессии и CSRF | 3 | 1 день |
| 5. Каталог и расписание | Публичные API, фильтры, кэш | 3 | 0,5 дня |
| 6. Бронирование | Транзакции, блокировка конфликтов, отмена и истечение | 4, 5 | 1,5 дня |
| 7. Администрирование | Фильмы, залы, сеансы, цены, журнал действий | 4, 5 | 1 день |
| 8. Интерфейс | Афиша, схема мест, кабинет, панель администратора | 5, 6, 7 | 2 дня |
| 9. Проверка | Модульные, интеграционные и нагрузочные тесты | 3–8 | 1 день |
| 10. Развёртывание | Docker, переменные среды, health check, инструкция | 9 | 0,5 дня |

Критический путь проходит через требования, схему БД, серверный каркас, учётные записи, бронирование, интерфейс и тесты. Документация API ведётся вместе с маршрутами, а не откладывается на последний этап.

## Ресурсы и роли

| Роль | Зона ответственности |
| --- | --- |
| Тимлид | План, границы версии, приёмка и интеграция |
| Системный аналитик | Требования, сценарии, модель данных и API-контракт |
| Backend-разработчик | SQLite, бизнес-правила, безопасность и REST API |
| Frontend-разработчик | Доступный интерфейс и интеграция с API |
| Тестировщик | Проверка правил, конфликтов бронирования, ролей и нагрузки |

В учебной реализации один исполнитель может последовательно выполнять роли, сохраняя перечисленные зоны ответственности.

## Риски

| Риск | Вероятность и влияние | Мера |
| --- | --- | --- |
| Два пользователя выбирают одно место | Средняя, высокое | `BEGIN IMMEDIATE`, повторная проверка и частичный уникальный индекс |
| Неоднозначность «покупки» без эквайринга | Высокая, среднее | Явно считать оплату учебной имитацией и хранить режим заказа |
| Ошибка часового пояса | Средняя, высокое | Хранить UTC, требовать часовой пояс в API, отображать локально |
| Слабый пароль администратора | Средняя, высокое | Передавать `ADMIN_PASSWORD`, использовать стойкий KDF, HTTPS и `Secure` cookie |
| Рост каталога замедляет чтение | Низкая, среднее | Индексы, короткий кэш и ETag; при масштабировании вынести кэш |
| SQLite ограничивает большое число записей | Низкая для учебной версии, высокое при росте | Слой доступа отделён; следующий шаг — PostgreSQL |

## Масштабирование

Для нескольких экземпляров приложения SQLite заменяется PostgreSQL, а локальный кэш и ограничитель запросов — Redis. Статические файлы отдаёт обратный прокси или CDN. Оплату следует вынести в отдельную интеграцию с идемпотентными webhook-событиями. Эти изменения не входят в текущую практическую работу, но учтены в границах модулей и схеме статусов.
