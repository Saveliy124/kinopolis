# Кинополис — практические занятия №1–12

Дисциплина: «Создание программного обеспечения». Тема проекта: монолитное веб-приложение кинотеатра. Стек: Python 3.9+, SQLite, HTML, CSS, JavaScript. Результаты проверки приведены на 22 октября 2026 года.

## №1. Введение и организация проекта

**Цель.** Определить предметную область, способ организации разработки и роли.

Выбрана автоматизация одного кинотеатра: публикация афиши, расписания и цен, выбор мест, бронь, учебная покупка, управление фильмами, залами и сеансами. Клиент, API и работа с данными составляют один развёртываемый монолит.

В плане выделены роли тимлида, системного аналитика, backend-разработчика, frontend-разработчика и тестировщика. Их зоны ответственности указаны в [плане разработки](../docs/development-plan.md). Состав реальной команды в отчёте не выдумывается.

**Результат.** Зафиксированы тема, архитектурный подход, роли и границы учебной версии. Основные компоненты описаны в [архитектуре](../docs/architecture.md).

## №2. Анализ требований и планирование

**Цель.** Сформировать функциональные и нефункциональные требования, варианты использования и план разработки с зависимостями.

Предметное описание разложено на роли гостя, пользователя и администратора. Для гостя нужны каталог и расписание; для пользователя — регистрация, выбор мест, бронь, покупка и отмена; для администратора — фильмы, залы, сеансы и цены. FR-01–FR-12 имеют проверяемые критерии. NFR описывают целостность, защиту паролей, сессии, производительность и переносимость.

Варианты UC-01–UC-05 описывают обычный сценарий и ошибки. Например, при занятом месте UC-02 требует отклонить весь заказ. Подготовлена [диаграмма сценариев](../docs/use-cases.mmd). HTML задаёт структуру интерфейса, CSS — оформление, JavaScript — действия пользователя и fetch-запросы к серверу. Сервер проверяет правила и возвращает JSON.

План включает анализ, модель БД, сервер, учётные записи, каталог, бронирование, администрирование, интерфейс, тестирование и развёртывание. Для этапов заданы оценки времени и зависимости. Риски: конкурентная продажа, часовые пояса, слабый пароль и рост нагрузки. Меры — транзакции, UTC, пароль администратора через окружение, индексы и кэш. Будущая замена SQLite на PostgreSQL рассмотрена как возможность масштабирования.

**Результат.** [Требования](../docs/requirements.md) и [план](../docs/development-plan.md) задают критерии приёмки и порядок работ.

## №3. Проектирование схемы базы данных

**Цель.** Определить сущности, атрибуты, отношения и ключи.

Выделены users, auth_sessions, movies, halls, seats, screenings, bookings, tickets и audit_log. Фильм и зал связаны с сеансами как один ко многим; зал содержит места; пользователь оформляет заказы; каждый заказ содержит билеты на места одного сеанса. Первичные ключи — INTEGER. Внешние ключи связывают сущности и защищают историю от удаления связанных записей.

Длительность, количество рядов, номера мест и цена хранятся целыми числами. Цена задаётся в копейках, чтобы исключить погрешности дробной арифметики. Время хранится текстом ISO 8601 в UTC. Адрес пользователя, название зала, место в зале и код заказа уникальны.

**Результат.** Созданы [ER-диаграмма](../docs/erd.mmd), [описание данных](../docs/database-design.md) и исполняемая [SQL-схема](../database/schema.sql).

## №4. Нормализация, производительность и защита БД

**Цель.** Уточнить ограничения, индексы, нормализацию и безопасность данных.

Данные пользователей, фильмов и залов вынесены в отдельные таблицы. Контролируемая денормализация применяется к screening_id и price_cents в билете и total_cents в заказе: она обеспечивает уникальность активного места и сохраняет историческую стоимость.

CHECK ограничивает роли, статусы и числовые диапазоны. Индексы ускоряют выборку расписания, истории пользователя и истёкших броней. Частичный уникальный индекс uq_active_ticket запрещает две активные продажи одного места на одном сеансе. BEGIN IMMEDIATE обеспечивает атомарность заказа. WAL позволяет читать во время записи, а каталог кэшируется на 30 секунд.

SQL использует параметры. Пароли хешируются с солью через scrypt или PBKDF2. Токен сессии хранится в БД только в виде хеша. Доступ к файлам и резервным копиям ограничивается правами ОС; шифрование файла SQLite в проекте не заявляется. Для передачи через публичную сеть предусмотрен HTTPS.

**Результат.** Схема выполняется на пустой БД; автоматическая проверка целостности и индексов проходит. Механизм [резервного копирования](../scripts/backup.py) проверяет целостность копии и учитывает WAL.

## №5. Реализация серверной логики

**Цель.** Создать сервер, бизнес-правила и API монолитного приложения.

Сервер на стандартной библиотеке Python раздаёт static-файлы и маршруты /api/. CinemaService реализует регистрацию, вход, каталог, расписание, оформление и отмену заказов, создание залов и сеансов, изменение фильмов и цен. Database управляет соединениями и транзакциями SQLite.

При бронировании сервер проверяет пользователя, сеанс, активность фильма и зала, принадлежность мест, отсутствие повторов и занятости. Допустимо 1–10 мест. Бронь действует 15 минут; учебная покупка получает статус paid. Истёкшая бронь освобождается при следующем обращении к заказам или местам. Уже оформленные билеты сохраняют первоначальную цену.

Между сеансами одного зала оставляется 15 минут на уборку. Схему зала нельзя менять при связанных билетах или будущих показах; длительность фильма с будущими сеансами также защищена от изменения. Ошибки возвращаются в общем формате JSON.

**Результат.** Реализована [серверная логика](../cinema/service.py); API описан в [OpenAPI](../docs/openapi.yaml).

## №6. Интерфейс, интеграция, безопасность и тестирование

**Цель.** Связать UI с сервером, добавить защиту и проверить работу приложения.

Сохранено исходное оформление «Кинополиса»: тёмный фон, красные акценты, карточки афиши и схема кинозала. JavaScript загружает каталог, фильтрует сеансы и отправляет выбранные места через fetch. Личный кабинет показывает статусы и отмену брони; административная панель доступна после входа с ролью admin.

Пароли не возвращаются клиенту. Сессионная cookie имеет HttpOnly и SameSite=Lax; изменяющие запросы требуют X-CSRF-Token. Роль проверяется сервером. Пользовательский текст вставляется через textContent. Применены CSP, ограничение тела запроса, лимит попыток входа, ETag, gzip и TTL-кэш. Схема занятости и личные ответы не кэшируются.

Модульные и интеграционные тесты проверяют пароли, схему БД, конфликт бронирования, роли, CSRF, ошибки и REST. Нагрузочный запуск выполнен на живом локальном сервере: 200 запросов, 20 клиентов, 200 успешных ответов. В браузере проверены вход, выбор мест, сумма, бронь и отмена.

**Результат.** Пройдено 28 автоматических тестов. Численные результаты и границы проверки указаны в [протоколе](../docs/test-results.md).

## №7. Развёртывание и серверное окружение

**Цель.** Выбрать инфраструктуру, подготовить окружение, права и запуск приложения.

Локальное развёртывание проверено на Windows и macOS: Python запускает сервер на 127.0.0.1:8000, схема и учебные данные создаются автоматически. Для Windows добавлен START.cmd. Проверка /api/health подтверждает работу сервера и существующей схемы БД.

Для отдельного сервера подготовлен Dockerfile на python:3.12-slim. В нём создаётся непривилегированный пользователь cinema и каталог /data с нужными правами. Compose хранит SQLite в томе и применяет restart: unless-stopped. Настройки передаются через окружение. Базовый порт опубликован только на loopback.

**Результат.** Локальный HTTP-сервер и Docker-контейнер работают. В контейнере подтверждены пользователь cinema, health, каталог и REST-сценарий. [Инструкция](../docs/deployment.md) описывает запуск на отдельном сервере.

## №8. Безопасность и мониторинг развёртывания

**Цель.** Предусмотреть защиту, наблюдение за состоянием и управление сервером.

Для публичного размещения добавлены Caddyfile и дополнительный Compose: обратный прокси выдаёт HTTPS-сертификат реального домена, приложение использует Secure-cookie. Инструкция описывает DNS, открытие 80/443, ограничение SSH, закрытие прямого доступа к 8000 и обновления ОС.

Docker health check обращается к /api/health каждые 30 секунд. Endpoint возвращает 503, если БД отсутствует или её схема недоступна, и не создаёт пустую БД при проверке. Отдельный check_health.py подходит для внешнего мониторинга. HTTP-запросы и исключения выводятся в журналы, административные действия записываются в audit_log. Backup API SQLite создаёт согласованную копию без остановки приложения и без потери данных из WAL. Резервная копия не перезаписывает существующий файл. Compose и прямой сетевой запуск требуют собственный пароль администратора.

**Результат.** Локальная проверка health, создание копии и запуск Docker проходят. Внешние сетевые правила и публичный сертификат требуют применения и проверки на целевом сервере с доменом. Порядок приёмки дан в [инструкции](../docs/deployment.md).

## №10. Проверка модели данных проекта

**Цель.** Сверить физическую схему с бизнес-правилами и API.

Сущности и связи остаются прежними: новые методы работают с существующими movies и bookings. PUT обновляет редактируемые атрибуты фильма, а DELETE отменяет бронирование без удаления истории. У заказа и его билетов согласованно изменяется статус.

Бронь создаётся одной транзакцией; при конфликте мест частичного заказа не возникает. Параллельный тест двух клиентов даёт один ответ 201 и один 409. Просроченная бронь освобождает место. Сохранённая цена билета не зависит от последующих цен сеанса. Индексы и целостность проверяются тестами; backup отдельно проверяется с открытой WAL-базой.

**Результат.** Схема и существующие индексы покрывают операции до №12 без дополнительных таблиц. Обоснование нормализации, оптимизации и защиты находится в [проектировании БД](../docs/database-design.md).

## №11. Разработка RESTful API

**Цель.** Определить ресурсы, методы, маршруты и форматы обмена.

Основные ресурсы — фильмы, сеансы, места, заказы и залы. GET /api/movies и GET /api/movies/{id} читают каталог; GET /api/screenings и GET /api/screenings/{id}/seats показывают расписание и доступность. POST /api/bookings создаёт заказ, GET /api/bookings/{id} читает собственный заказ, DELETE /api/bookings/{id} отменяет бронь.

Администратор создаёт фильм через POST /api/admin/movies, заменяет все пять редактируемых полей через PUT /api/admin/movies/{id} или изменяет часть через PATCH того же адреса. POST используется также для залов и сеансов, PATCH — для параметров зала и цены.

Запросы и ответы используют JSON. Создание заказа возвращает 201 и Location, DELETE — 204 без тела, неверный метод — 405 и Allow, OPTIONS перечисляет допустимые методы. Валидация даёт 422, конфликт — 409, неизвестный ресурс — 404. DELETE повторяется безопасно: история остаётся cancelled.

**Результат.** Все 22 операции описаны в OpenAPI 3.0.3. Спецификация прошла структурную проверку и сопоставление с маршрутами. [Демонстрация](../scripts/demo_api.py) выполняет GET, POST, PUT, PATCH и DELETE по настоящему HTTP.

## №12. Защита и проверка REST API

**Цель.** Реализовать аутентификацию, авторизацию и защиту данных API.

После входа сервер выдаёт cookie и CSRF-токен. Без сессии защищённый маршрут возвращает 401; пользователь без роли admin получает 403. Каждый изменяющий защищённый запрос проверяет CSRF. Чужой заказ возвращает 404, поэтому по API нельзя раскрыть его содержимое или отменить его.

Неверный JSON возвращает 400, неверный Content-Type — 415, дробные и логические идентификаторы — 422. Режим заказа проверяется до бизнес-операции. Личные данные и ошибки имеют Cache-Control: no-store. Запросы используют параметры SQL, а сообщения внутренних ошибок не содержат трассировку.

Проверены получение чужой брони, DELETE без CSRF, запрет отмены покупки, повторный DELETE, PUT обычного пользователя, неполный PUT, методы OPTIONS/405 и конкурентное оформление. Старый POST /cancel оставлен совместимым и помечен deprecated в OpenAPI; интерфейс использует DELETE.

**Результат.** API интегрирован с интерфейсом; 28 тестов и реальный HTTP-сценарий проходят. Docker-контейнер проверен локально; публичный HTTPS остаётся пунктом приёмки на целевом сервере.
